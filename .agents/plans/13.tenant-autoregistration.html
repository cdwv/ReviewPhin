Plan 13 · tenant onboarding

Let a trusted first webhook register its project.

Operators currently register every tenant before ReviewPhin can accept its webhooks. Connections should be able to opt into safe automatic registration while preserving platform access checks, webhook authentication, and predictable model selection.

ImportanceHigh
Who noticesOperators and project teams
Main areaWebhook onboarding
Stored dataConnection defaults and policy
Finished result: an operator can enable an existing GitHub or GitLab connection, hand a team the correct setup bundle, and let the first authenticated webhook create the tenant. The same webhook then continues through normal event handling.

What is wrong today?

An unknown project always stops

The webhook route identifies a project, looks for its tenant, and returns not found when no tenant exists. It has no safe path for creating one.

GitLab does not identify the connection

A GitLab event names its instance and project, but not the ReviewPhin bot credential that should own the tenant. Several connections can also reach the same instance.

A first-time secret cannot trust itself

Accepting any secret supplied by an unknown first request would let a forged payload choose the credential that protects all later requests for that tenant.

Profiles have no connection fallback

A review can use a review override, a tenant override, or the instance default. An operator cannot yet choose one live default for all non-overridden tenants on a connection.

What do we want instead?

1. Authenticate and routeProve the webhook and identify one enabled, ready connection before remote API work.
2. Verify platform accessRequire GitLab Developer access or GitHub App installation access to the named project.
3. Create and continueCreate the tenant once, then process that same event through the ordinary webhook path.
  • Automatic registration is off for every new and migrated connection.
  • An existing ready connection can enable or disable it without recreating credentials.
  • Unsupported platform modules cannot opt in accidentally.
  • An existing tenant is never reassigned or overwritten by a webhook.
  • Concurrent first deliveries converge on one tenant.
  • Profile order is review override, tenant override, connection default, instance default, then native fallback.

How do we fix it?

Situation Planned behavior
Connection administration Add opt-in automatic registration and an optional live default profile. Support enabling, disabling, clearing the profile, showing onboarding data, and rotating future onboarding credentials on existing connections.
GitHub first webhook Match its App installation to one enabled connection, verify the signature, and use installation credentials to load the repository before registration.
GitLab 17 and later Use a connection-specific URL and a high-entropy custom bootstrap header. After that check, store and verify the project-specific legacy webhook token supplied with the request.
GitLab 19.0 with signing enabled, and GitLab 19.1 or later Allow a signing token in addition to the legacy token. Verify the raw body, webhook ID, and recent timestamp, and copy the verified signing credential into the new tenant.
Access denied or request forged Create nothing, reveal no candidate details, and return the same not-found response used for an unavailable tenant.
Temporary API or storage failure Record a secret-free diagnostic and return a retryable server error instead of pretending the project is ineligible.
No trust on first use: remote project access proves that ReviewPhin can serve a project; it does not prove that an incoming GitLab request came from that project. The bootstrap check must succeed before accepting or storing its project secret.

Work steps

  1. Store common connection policy. Add the disabled-by-default registration switch and nullable connection profile to the storage contract. Migrate both built-in storage providers without changing existing connection behavior.
  2. Make connection settings independently editable. Let metadata-only changes bypass provider credential recreation. Validate profile references, expose positive and negative switches, and report the effective settings in every output mode.
  3. Provide a safe onboarding bundle. Give an operator a copyable webhook URL, GitLab bootstrap header, suggested project token, and version-labelled signing guidance. Reveal secrets only through an explicit onboarding action.
  4. Add the platform capability. Let a platform declare support and return an authenticated connection plus normalized tenant settings. Keep storage writes and existing tenant conflict rules in the shared registry.
  5. Implement GitHub registration. Authenticate with the matched App connection, prove repository access, build the same tenant settings as manual registration, and preserve normal check-run setup.
  6. Implement GitLab registration. Route by the connection-specific URL, verify bootstrap and webhook credentials, require Developer-or-higher effective access, and retain GitLab 17 legacy authentication.
  7. Make creation race-safe. Add one create-or-get operation keyed by the remote project. A losing request must load the winner, continue only for the same connection, and never change tenant secrets or ownership.
  8. Apply live profile fallback. Resolve the connection profile after a missing tenant override and before the instance default. Block profile deletion while either a tenant or connection still references it.
  9. Document operations and failures. Cover setup by GitLab version, GitHub App repository selection, disabling future registration, credential rotation, retry behavior, and audit-safe diagnostics.

How do we know it works?

  • New and migrated connections reject unknown tenants until an operator explicitly enables automatic registration.
  • Enabling an existing GitLab connection produces a usable URL and bootstrap bundle without recreating its API credential.
  • GitLab 17 accepts a correctly bootstrapped legacy webhook and rejects a missing bootstrap header, bad tenant token, or access below Developer without storing anything.
  • GitLab 19 verifies a valid signing signature when the feature is available, in addition to the tenant token, and rejects altered bodies, stale timestamps, and downgrade attempts.
  • GitHub selects only the payload's installation, verifies its signature, and refuses repositories outside that installation.
  • Two simultaneous first deliveries yield one tenant, and a tenant already owned by another connection is unchanged.
  • The webhook that creates a tenant can also create or handle its intended event; no second delivery is required.
  • Changing a connection or instance default changes the next review for tenants without a higher override, while explicit tenant and review overrides still win.
  • Pretty, plain, JSON, and logs never reveal onboarding, webhook, App, or API secrets unless the operator invokes the explicit onboarding action.
