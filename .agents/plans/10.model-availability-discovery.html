Plan 10 · model configuration

Show which models the current credentials can actually use.

A model profile accepts any non-empty model name. The first proof that a Copilot account cannot use that model may arrive only when a session starts. Operators need discovery and save-time validation that reflect the credentials in use.

ImportanceMedium
Who noticesOperators
Main areaModel profile CLI
Stored dataNo change
Finished result: an operator can list the models available to the active Copilot identity, inspect useful capabilities, and validate a complete profile before it is saved. Missing or unverifiable models prevent the write unless the operator explicitly uses --ignore-missing-model. ReviewPhin does not repeat this check when a saved profile is selected or used.

What is wrong today?

Saved does not mean usable

The CLI checks that a name exists as text, not that the account or provider recognizes it.

Availability belongs to credentials

Two accounts can receive different model catalogs. A static list in documentation would become wrong for some operators.

Provider discovery is uneven

Native Copilot exposes a catalog, while custom providers do not all implement the same model-list endpoint or metadata.

Invalid settings remain stored

A misspelled model can become the default or be assigned to a tenant. The eventual session error is useful, but the CLI had an earlier chance to prevent the invalid save.

What do we want instead?

1. Select credentialsUse the fallback Copilot identity or a named saved profile.
2. Discover or checkAsk the provider when supported and show capabilities it reports.
3. Save or rejectWrite a valid profile, reject the command, or honor the explicit override.
  • The catalog is live and credential-specific, not hard-coded.
  • Native Copilot model listing works in pretty, plain, and JSON output.
  • New and updated profiles are checked before storage changes.
  • Missing or unverifiable models reject the command by default.
  • --ignore-missing-model explicitly permits an unvalidated profile to be saved.
  • An omitted model is valid and uses the Copilot CLI default; it does not require validation.
  • Selecting a default profile and running model sessions do not perform catalog checks.
  • Providers without discovery say so honestly instead of silently accepting the profile.

Work steps

  1. Add the fixed command contract. Add the catalog command and save-time flag with the output, warning, and exit behavior specified below.
  2. Expose the Copilot catalog. Start the existing client with the same authentication and CLI settings as reviews, list models, then stop it cleanly.
  3. Validate explicit models before saving. Combine new values with the existing profile, skip null model IDs, validate every effective explicit model, and only then write the profile. Keep existing data untouched on every validation failure.
  4. Honor the override visibly. Attempt validation even when the flag is present. Save after a missing or unavailable result, but emit the required warning and structured validation status.
  5. Document the boundary. Explain that catalogs vary by account and time, custom-provider discovery may be unavailable, null uses the Copilot default, and runtime does not revalidate saved profiles.
Catalog command output: model-profile available-models exits zero and sorts models by ID. Pretty output is a table with Model, Name, Reasoning, Default effort, and Vision columns. Plain output uses one tab-separated row per model in that order. JSON output is {"source":"github-copilot","models":[...]}; each model contains id, name, supportedReasoningEfforts, defaultReasoningEffort (nullable), and supportsVision. Catalog or authentication failure exits one and uses the JSON error code model_catalog_unavailable.
Profile validation output: a confirmed missing model without the flag exits one, writes nothing, and uses model_not_found with profileName and sorted missingModels in JSON. An unavailable validation exits one with model_validation_unavailable. Successful JSON keeps the existing profile fields and adds modelValidation with status, sorted checkedModels, and sorted missingModels. Status is validated, not_required, ignored_missing, or ignored_unavailable.
Required override warning: for every confirmed missing model, pretty and plain output say Model "<id>" was not found, but --ignore-missing-model was provided, so this result was ignored. The command still exits zero and saves the profile. If validation itself is unavailable, use the same pattern but say availability could not be verified. Never claim a model is missing without a successful catalog response.
Technical notes for the implementing agent
  • The installed SDK exposes CopilotClient.listModels(); current production use is visible in harness session image capability checks.
  • Add the command alongside existing model-profile CLI commands and reuse the safe output layer in CliOutput.
  • Profile resolution and provider construction live in model profile resolution. Build the effective updated profile before validation so omitted command options retain their stored values. Keep stored secrets masked in all output and errors.
  • The non-mutating merge used for validation must match the existing partial-update rules in storage helpers and the SQLite adapter. Extract or share a pure resolver rather than copying the rules into the CLI.
  • Perform catalog validation before storage.upsertModelProfile. This also prevents a failed model-profile add --default command from changing the existing default.
  • A null native Copilot review model requires no validation. A null text-generation model inherits the review model; validate that explicit inherited ID once. Custom providers still require their existing explicit review model.
  • Do not add validation to model-profile set-default, tenant assignment, or harness runtime. A reliable existing missing-model error may be made non-retryable without another catalog request, but that is optional and is not an acceptance requirement.
  • Extend CLI help tests, CLI output tests, harness client tests, and model profile tests. Assert that the storage write is not called after a missing model, unavailable discovery, authentication failure, or catalog failure, and that the override flag still attempts validation and then permits the write. Add regression coverage proving null models, set-default, and harness startup do not trigger catalog validation.
  • Update model profile guidance and the CLI reference with the new command, flag, output contract, null behavior, and lack of runtime revalidation.
  • Track the original request in GitHub issue 28.

How do we know it works?

  • The command lists only models returned for the current Copilot credentials.
  • Pretty output is readable, plain output has no ANSI escapes, and JSON output is stable and machine-readable.
  • Review and text-generation models are checked independently.
  • A null review model saves without a catalog check and continues to select the Copilot CLI default. A null text-generation model continues to inherit the review model.
  • Adding or updating a profile with a missing model exits with an actionable error and leaves stored data unchanged.
  • A catalog, authentication, or unsupported-discovery failure leaves stored data unchanged by default and returns the specified stable error.
  • The override flag still attempts validation. A confirmed missing model produces the required warning and an ignored_missing result before the profile is saved.
  • Unavailable validation with the override produces an honest warning and an ignored_unavailable result before the profile is saved.
  • model-profile set-default, tenant assignment, and all model session startup paths make no new catalog calls.
  • No authentication token appears in normal output, JSON, logs, or errors.
