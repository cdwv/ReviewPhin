Plan 07 · model reliability

Repair invalid structured output inside the harness.

A model can return useful content that is not valid JSON or does not match the requested shape. ReviewPhin currently lets that failure escape the harness. Every structured harness call should make two focused correction attempts before it fails.

ImportanceHigh
Who noticesAll model-backed features
Main areaHarness sessions
Stored dataAttempts in run logs
Finished result: when any structured harness call returns malformed JSON or data that fails its requested shape, ReviewPhin asks the same model session to fix the response up to two times. The harness returns the first valid result or throws one clear error after both corrections fail.

What is wrong today?

Useful content can be rejected

One missing escape or required field makes the entire response unusable even when most of the review is present.

The retry is too broad

A normal job retry reloads context and asks for new work. That costs more and can produce different content instead of repairing the response already produced.

The error lacks repair context

Callers receive the invalid result and decide how to fail. Operators cannot easily tell which correction was attempted or why the final response still failed.

Blind text cleanup is unsafe

Replacing quotes or punctuation in arbitrary model text can silently alter code examples and finding content. Validation, not guesswork, must decide whether a response is usable.

What do we want instead?

1. ValidateParse the first response and check the requested object shape.
2. CorrectGive the model the failure details and request only a corrected object, at most twice.
3. Accept or failReturn the first valid correction or throw after the second correction fails.
  • Correction attempts happen inside the harness session.
  • Reviews, chatter, memory, and future structured calls use the same behavior.
  • Exactly two correction messages are allowed.
  • Malformed JSON and invalid object shapes are both eligible.
  • Every candidate passes the same parser and schema.
  • No heuristic quote replacement is used as a success path.
  • Logs distinguish the original response from corrections.

How do we fix it?

Problem Planned change
The first response is malformed. Keep the session open and ask for a corrected object using a concise JSON parsing failure.
The object parses but has the wrong fields. Summarize the validation failures without exposing secrets or excessive prompt content.
A correction is still invalid. Send no more than two correction messages. If the second correction is invalid, throw one clear terminal error from the harness.
The call does not request structured output. Keep its current behavior. Only calls with a requested output shape enter correction.
The harness owns recovery: callers receive valid structured data or one error after two failed corrections. They do not inspect a parse failure and decide whether to ask the model again.

Work steps

  1. Encode one fixed policy. Treat JSON parsing and object-shape validation failures as repairable, allow exactly two correction messages, and define the terminal error.
  2. Keep recovery inside the harness. Allow two messages after an invalid response without rebuilding the calling feature's context or returning the parse failure to it.
  3. Validate every answer identically. Send original and corrected candidates through the same extraction and schema checks.
  4. Record each attempt safely. Add attempt numbers, failure reasons, duration, and model usage to the existing run artifacts and metrics without logging secrets.
  5. Cover every structured caller. Test a valid first response, JSON repair, shape repair, two exhausted corrections, and unchanged unstructured-call behavior across reviews, chatter, and memory work.
Technical notes for the implementing agent
  • Start with HarnessSessionRuntime.run and parseHarnessStructuredResponse. The session runtime should own the send, parse, validate, and two-correction loop.
  • Structured consumers include HarnessReviewProvider.review, harness chatter, and memory consolidation. They should all receive the same harness behavior whenever they provide a responseFormat.
  • After two invalid corrections, throw a stable harness error that preserves the last parse or Zod validation detail. Keep whole-job retry handling unchanged as the outer recovery boundary; no special combined retry budget is required.
  • Add focused cases to harness session tests , review provider tests, chatter tests, and memory service tests.
  • This work should not change the storage contract. Use existing per-session logs and the existing completed result field.
  • Track the original report in GitHub issue 27.

How do we know it works?

  • A response with invalid JSON is corrected without leaving the harness session.
  • A schema-invalid response receives concise, useful validation guidance.
  • A valid first response causes no correction call.
  • Reviews, chatter, and memory consolidation all use the same two correction limit when they request structured output.
  • Two invalid corrections produce one stable harness error and then follow normal caller and job retry rules.
  • No test accepts content because of blind quote or punctuation replacement.
  • Calls without a requested output shape do not enter correction.

Checks to run: harness session tests, review provider tests, chatter tests, memory service tests, worker retry tests, run-log and metrics tests, pnpm test, pnpm typecheck, and pnpm build.
