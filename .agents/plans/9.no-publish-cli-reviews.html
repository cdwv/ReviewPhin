Plan 09 · local CLI test

Review a remote change without writing back to its platform.

The CLI can submit a review of an existing merge request or pull request, but a successful run follows the normal publication path. Operators need a mode that reads remote context, runs the model, and acts as a local test: it delivers the result locally while guaranteeing zero platform mutations and retaining the result in ReviewPhin storage.

ImportanceMedium
Who noticesReviewers and operators
Main areaReview CLI and worker
Stored dataJob, run, result, and diagnostic records
Finished result: mr review --no-publish and its exact alias --no-comment read an existing remote review, perform the full analysis, and save the checked result to storage. By default, the CLI prints a readable report; with --report/-r <path>, the invoking CLI writes a Markdown report to its own filesystem, replacing the file if it already exists. The run creates or updates nothing on GitLab or GitHub.

What is wrong today?

Local submission still publishes

The command originates locally, but the worker reconciles findings into remote discussions and summaries.

The result is hidden behind job status

The watch view reports progress and counts. It does not present the completed review as useful formatted console text or a Markdown file.

“Dry run” would be misleading

The operation still reads the remote platform, calls a model that may incur cost, and writes configured storage and run-log records.

There is no report artifact option

The existing --output option selects console data format, not a destination. A separate --report/-r option must write the final review to a file, and the CLI must learn to parse that short option.

What do we want instead?

1. CLI queues and watchesSubmit the local-test job with its publication choice, then watch the stored job and run state.
2. Runner analyzes and storesRun the normal review, save the checked result, and omit every platform publication step.
3. CLI collects and deliversLoad the completed result from storage, then print formatted text or write the Markdown report.
  • The default command keeps its current publication behavior.
  • --no-publish and --no-comment are exact aliases with the same help text and behavior.
  • Either alias means zero platform writes, not zero platform reads.
  • A no-publish run is explicitly a local test.
  • The checked review result is saved to configured storage.
  • With no file destination, the final review is printed as readable, well-formatted console text.
  • With --report/-r <path>, the final review is written by the invoking CLI as valid Markdown to that path instead of being printed as the console report. An existing destination file is overwritten with the new complete report.
  • Combining --no-watch with --report/-r fails before a review job is submitted.

How do we fix it?

Area Planned behavior
Command option Add --no-publish and the easier-to-remember --no-comment alias. Treat them as one publication choice. Do not call this a dry run because model work and storage writes still happen.
Output destination Print a polished text report to the console by default. When --report/-r <path> is supplied, the invoking CLI—not the runner—writes the same review as valid UTF-8 Markdown to the requested file, replacing rather than appending to an existing file. Continue to use the existing --output option only for the format of progress, diagnostics, and other CLI data.
Invalid option combination Reject --no-watch together with --report or -r with the error “Cannot combine --no-watch with --report or -r.” Validate this before any job is queued.
CLI responsibility Queue the job, watch it to completion, load and validate the stored checked result, build the report, and either print it or write it to the caller-local file. Keep the report path and presentation choices in the CLI process.
Runner responsibility Read the publication choice from the queued request. Otherwise perform the normal review and storage work, but bypass every platform publication path. The runner does not format output, write the report file, or receive its path.
Remote safety Skip every platform mutation, including emojis or reactions, inline and summary comments, responses or replies, discussion reconciliation, GitHub review submissions and statuses, check statuses, trigger-status updates, cleanup, and platform-hosted project memory writes.
ReviewPhin storage Complete the interaction run with the checked review result in the configured storage provider. Retain normal job and run records, diagnostics, artifacts, logs, and metrics even though nothing is published to the code-review platform.
CLI report Build one canonical Markdown report. Render its headings, lists, code, suggestions, severity, and file anchors cleanly for a terminal, or write the Markdown source to the selected file.
Zero remote writes is a contract: tests must fail if any GitLab or GitHub mutation endpoint is called, even for progress feedback, an emoji, a comment or response, a GitHub review or status, cleanup, platform memory, or an error path.
Keep format and destination separate: --output continues to choose pretty, plain, or JSON CLI data. --report/-r only redirects the final review artifact to a Markdown file; it does not change the global output format.
Local-test report contract: --report/-r belongs to a watched no-publish run. The CLI process that submitted and watched the test writes the file after loading the checked result from storage. Combining it with --no-watch is an error and queues nothing. Progress and diagnostics may still use the console; only the final review artifact has one destination.
The runner integration stays narrow: the queued publication choice is the only new input the runner needs. It does not receive the report destination or CLI output settings. Its only changed behavior is to skip platform publication while preserving normal analysis, result storage, diagnostics, metrics, artifacts, and cleanup.
Overwrite is intentional: once the watched run has a checked result, --report/-r replaces any file already at the selected path with one complete Markdown report. It never appends. A run that fails before producing a checked result does not start the write, so an existing file remains unchanged.

Work steps

  1. Add a report destination. Add --report <path> and its -r alias without changing the global output-format option. Add short-option parsing and reject --no-watch together with either report spelling before platform setup, storage access, or job submission. Replace an existing destination only after the completed report has been built in memory.
  2. Persist one publication choice. Extend the local review request with a backward-compatible publication mode. Map --no-publish and --no-comment to that same value and expose both in help. Do not queue the report path or presentation settings.
  3. Fence only platform publication in the runner. Read the queued publication choice once and bypass every mutation path while retaining platform reads, workspace hydration, analysis, storage, diagnostics, metrics, artifacts, and cleanup.
  4. Collect the result in the CLI. After the watcher observes terminal completion, make the CLI load and validate the checked result from configured storage. Do not add report rendering or file-writing responsibilities to the runner.
  5. Create one report formatter. Convert overview, readiness, findings, anchors, explanations, and suggestions into canonical Markdown. Render it with terminal styling and width-aware wrapping for console delivery, or write it without terminal escapes to the chosen Markdown file.
  6. Prove the safety boundary. Run successful, failed, retried, GitLab, and GitHub no-publish jobs against clients that reject every mutation call. Exercise both aliases, console delivery, file delivery, and stored-result retrieval.
Technical notes for the implementing agent
  • Extend localReviewTriggerSchema with a backward-compatible publication mode. Existing stored triggers must continue to mean normal publication.
  • Global output parsing is implemented by resolveOutputMode, and parseCliArgs currently recognizes only long options. Keep --report out of resolveOutputMode, and extend argument parsing narrowly enough that -r cannot consume a command name or another option by accident.
  • The CLI submission and wait path lives in runMergeRequestReviewCommand and watchReviewJob.
  • watchReviewJob currently returns ReviewWatchSummary, which has a run ID and counts but not the stored review payload. After a successful watch, keep result collection in runMergeRequestReviewCommand: load that interaction run, parse its resultJson with reviewResultSchema, then render or write the report. Do not add file-output arguments to the watcher or worker.
  • The main mutation boundary is the review worker, especially discussion reconciliation and chatter publication. Local triggers already use NoOpPlatformTriggerLifecycle.
  • In the worker, the publication mode should only guard platform mutation calls such as discussion reconciliation, chatter reply publication, and lifecycle updates. Keep the normal reviewer, finding persistence, completeInteractionRun, metrics, run artifacts, and workspace cleanup paths unchanged.
  • Parse the stored result with reviewResultSchema. Add a dedicated report module rather than coupling terminal rendering to platform summary comments.
  • Add any Markdown parser/renderer as a direct production dependency. Do not rely on documentation-tool transitive dependencies.
  • A caller-side output file requires a watched terminal result. Reject --report/-r with --no-watch during input validation, before initializePlatformRegistry, withStorage, or createOrGetInteractionJob. Cover both report spellings with the same human-readable validation error.
  • Keep the report path out of localReviewTriggerSchema. The runner may be on another machine. After watchReviewJob returns a completed result, the invoking CLI resolves the caller-local path and writes the Markdown file. Build the full report before opening the destination, then replace its contents rather than appending. A filesystem write error must fail the command.
  • No new storage column is expected because the trigger JSON and existing interaction result are sufficient.

How do we know it works?

  • The same remote change can be reviewed with and without publication, and the default remains unchanged.
  • A no-publish run makes remote read calls but no remote mutation calls in success, retry, or failure paths. This includes emojis, comments, responses, GitHub reviews, and GitHub check statuses.
  • --no-publish and --no-comment produce the same queued publication mode and the same observable behavior.
  • The queued request contains the publication choice but never the report path or console-format settings.
  • The runner stores the same checked result shape as a publishing run; its only no-publish difference is that no platform mutation path is called.
  • After completion, the CLI uses the watched run identity to load and validate the stored result before it prints or writes the report.
  • Default console output has readable headings, lists, code blocks, severity, and file anchors at narrow and wide terminal widths.
  • --report and -r write the same valid Markdown file without terminal escape codes, and do not also print the final console report.
  • When the report path already exists, its previous contents are replaced by exactly one complete new report; no old content is retained or appended.
  • A review failure before report generation leaves an existing destination unchanged, while a filesystem write failure returns a non-zero exit code.
  • --no-watch --report <path> and --no-watch -r <path> both fail with a clear incompatibility error before platform setup, storage access, or job creation; neither creates or changes the report file.
  • The checked review result, job and run records, metrics, logs, and diagnostic artifacts remain available through the configured storage provider.
