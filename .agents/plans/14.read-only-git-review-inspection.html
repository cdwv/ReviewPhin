Plan 14 · review quality

Let the reviewer inspect every change through safe, read-only Git.

ReviewPhin currently chooses a small number of changed files for the starting prompt. Replace that hard limit with a complete, compact change list and a dedicated Git inspection tool, so the reviewer can widen its work without loading every diff up front.

ImportanceHigh
Who noticesTeams with larger changes
Main areaReview context and tools
Stored dataNo schema change
Finished result: every review starts with the full change boundary, then reads diffs, history, blame, and files only as needed. Large reviews are neither silently partial nor bloated with every full diff.

What is wrong today?

A file-count limit decides the starting scope

A first review receives at most 12 detailed changes, an incremental review receives 8, and a discussion follow-up receives 4. The model can read the workspace, but it may never learn that a later changed file deserves attention.

The fallback file list is incomplete

Only part of the omitted file list reaches the prompt. In the July sample, none of the 103 findings landed on a changed path beyond that visible list. That is evidence of a discovery gap, not proof that later files were safe.

Existing reads compensate, but do not close the gap

Most tool calls open files or search for related symbols. Among 21 capped first reviews, 644 of 896 changed files started outside the detailed scope and 288 were never reached by a file read or search. Recent logs are the most reliable because older sessions were not always stored completely.

Sending more full diffs would create a different problem

Putting every patch in the initial prompt would make ordinary reviews larger and can distract the model with low-value detail. The reviewer needs the whole map first and the full text on demand.

What do we want instead?

1. Prepare trusted revisionsMaterialize the exact review head and comparison base, then remove credentials and remote access.
2. Start with the whole mapDerive every changed path, change kind, and size from the local Git comparison without embedding patch bodies.
3. Inspect evidence on demandUse fixed read-only Git operations together with file reads and searches, then return the same focused review format.
  • First and incremental reviews have no numeric changed-file limit.
  • Discussion follow-ups remain focused by the target thread, not by an arbitrary file count.
  • The prompt always names every file inside the exact local Git comparison.
  • Git-ready sessions omit full diff bodies from their initial context while retaining change kinds and sizes.
  • The reviewer gets no general shell, network access, credentials, mutable Git operation, or path outside its workspace.

How do we fix it?

Problem Planned change
A fixed number of files receives detailed treatment. Remove file-count selection from full and incremental review discovery. Keep priority markers for the newest delta, open findings, and the requested discussion without hiding the rest of the review.
Complete patches would make the prompt too large. For Git-ready workspaces, replace inline patch bodies with one complete manifest containing paths, status, additions, deletions, object identities, and the trusted revisions. Discussion follow-ups inspect their target through the same read-only tool.
A general shell would be too broad. Register one dedicated tool that maps a small operation list to fixed Git commands. Each operation validates its own arguments and runs Git directly without a shell.
Git output can still overwhelm a session. Apply time and output limits per call. When output is cut off, return an explicit message that tells the reviewer to narrow by path, revision, or line range.
Repository preparation can fail. Use the complete platform diff only when it fits the fallback prompt budget. Otherwise stop the review clearly instead of publishing a result that silently skipped changes.
Read-only must be structural: do not accept a command string and do not depend on the model choosing safe flags. The server owns the executable, working directory, environment, operation map, revisions, argument rules, timeout, and output limit.

Work steps

  1. Lock down the expected review boundary. Add fixtures for large first reviews, large incremental reviews, renamed and deleted files, binary changes, forked pull requests, and focused discussion follow-ups. Preserve the current July session analysis as the before-deployment comparison.
  2. Prepare both trusted Git revisions. Update GitLab and GitHub workspace creation to fetch the exact head and comparison commits, create fixed local refs, check out the head without a branch, remove the remote, and discard all authentication data before the model session begins.
  3. Add the dedicated inspection tool. Register it only for reviewer sessions. Validate every operation separately, reject unsafe flags and paths, run without a shell, disable pagers and external diff helpers, and make truncation visible.
  4. Replace selection with compact discovery. Build one complete manifest directly from the trusted revisions before starting the reviewer. Remove numeric file limits and inline diff bodies when Git inspection is available, while preserving delta and discussion priorities. Keep provider patches only for publication details and non-Git fallbacks.
  5. Make degraded behavior explicit. Treat the Git comparison as the main review boundary on both platforms. If Git preparation or manifest parsing fails, use a complete inline provider fallback only when it fits; otherwise fail before review publication with a useful retry reason.
  6. Deploy, then inspect real sessions after one week. Repeat the same log analysis by review size and mode. Compare tool operations, changed paths reached, tool rounds, context tokens, failures, truncations, and where findings land. Use that evidence to tune prompt guidance or output limits rather than adding another file cap.
Technical notes for the implementing agent
  • Add git_readonly to HarnessToolId and register it from resolveHarnessTools with the Copilot SDK’s parameters field. Prefer a separate src/harness/git-readonly.ts implementation and focused unit test.
  • The operation enum should cover status, diff, log, show, list-branches, rev-parse, ls-files, and blame. Do not expose branch with arbitrary arguments because it can create or delete branches. If the schema keeps a generic args array, validate it against a separate allowlist for each operation.
  • Execute Git with execFile or spawn("git", args, { shell: false }) in the fixed, resolved workspace. Reject absolute paths, parent traversal, pathspec file loading, configuration overrides, aliases, --exec-path, --no-index, --output, external diff, text conversion, and every mutating operation. Resolve accepted paths and ensure they stay inside the repository.
  • Build a minimal Git environment with GIT_TERMINAL_PROMPT=0, GIT_OPTIONAL_LOCKS=0, GIT_PAGER=cat, GIT_CONFIG_NOSYSTEM=1, GIT_CONFIG_GLOBAL pointing to a known empty file, and GIT_LFS_SKIP_SMUDGE=1. Clear inherited Git configuration injection, credential, askpass, authorization, pager, and external-diff variables. Pass --no-ext-diff and --no-textconv where supported.
  • Extend PlatformMaterializedWorkspace and review context types with an in-memory inspection capability and fixed reviewphin/base and reviewphin/head refs. These are runtime values, not a storage-contract revision.
  • Change WorkspaceMaterializer.materializeFromGit to fetch the latest merge-request version’s base and head, retain .git, detach at the exact head, and remove origin before returning. Keep SHA verification and the archive and targeted-file fallbacks.
  • Replace archive-only preparation in GitHubWorkspaceMaterializer with authenticated exact-SHA Git preparation for the pull request base and head, including forks. Expose installation authentication to workspace setup without logging or retaining the token, then remove the remote before review.
  • In buildScopedReviewContext, remove CHANGE_LIMIT_BY_MODE and file slicing. Keep follow-up targeting and incremental priority rules. In buildCompactReviewContext, replace selected and omitted file arrays with the complete Git-derived manifest for Git-ready sessions and remove inline diff bodies.
  • Enable the new tool only in HarnessReviewProvider.review. Do not add it to chatter or memory sessions. The existing custom-tool permission path in HarnessSessionRuntime.run may approve it because the handler itself has no write path.
  • Preserve custom-tool name, operation, safe arguments, duration, truncation, rejection, and failure in HarnessRunLog events, but never record environment variables, credentials, or remote URLs. No new database fields are required.
  • Extend GitLab workspace tests, GitHub workspace tests, scope tests, prompt tests, review provider tests, and session tests. Add adversarial tests for every rejected operation and flag, path escape, malicious repository config, external diff and pager execution, timeout, output truncation, missing refs, malformed Git manifest output, and Git-unavailable fallback.
  • One week after deployment, run pnpm cli metrics sessions --from 2026-07-01 --all-sessions --json and analyze the corresponding recent reviewer logs. Compare pre/post sessions within similar changed-file bands and review modes; older logs may be incomplete.

How do we know it works?

  • A review with more than the old limit names every path found in the exact base-to-head Git comparison, with no “additional files” cutoff.
  • Git-ready first, incremental, and discussion-follow-up prompts contain no provider patch bodies; detailed evidence is read through the bounded Git tool.
  • The reviewer can compare the trusted base and head, inspect one path, read history and blame, and combine those results with normal file reads and searches.
  • Attempts to mutate the repository, invoke a shell or helper, write output, escape the workspace, use configuration injection, contact a remote, or exceed limits are rejected or stopped.
  • GitLab and GitHub verify exact revisions, remove remotes and credentials before review, and clean the complete workspace after success, failure, cancellation, or retry.
  • Git preparation failure never produces a silently partial review: the run uses a complete bounded fallback or fails clearly before publication.
  • The one-week production comparison reports Git operation mix, rejected and truncated calls, changed paths reached beyond the old limits, tool rounds, context use, failures, and finding locations.
  • The change uses existing run logs and adds no storage contract, SQLite migration, or Flotiq migration.

Checks to run: focused Git tool, workspace, scope, prompt, provider, session, fallback, and cleanup tests, pnpm test, pnpm typecheck, pnpm lint, and pnpm build.
