Draft Plan 14 · finding lifecycle

Give every review finding one durable key from creation to closure.

A finding saved without publishing has no GitHub or GitLab thread. Today the reviewer can close only findings that have a thread, so a fixed local finding can remain open forever. The revised contract gives the reviewer one finding key that works with or without a published comment.

Finished result: the reviewer copies one durable finding key when it continues, replaces, resolves, or dismisses an earlier issue. ReviewPhin updates the saved finding and, when one exists, the matching platform thread. No-publish and published reviews follow the same finding rules.

What is wrong today?

Local findings have no way to close

A no-publish review saves a finding but creates no platform thread. A later review can see that the issue is fixed, yet it cannot name the saved finding in its closure instructions.

Readiness can remain wrong forever

Once old findings correctly count toward readiness, an old local finding stays active across every later review. Reports continue to say that work is needed after the code is fixed.

The reviewer sees several kinds of identifiers

Saved findings, ReviewPhin discussion mappings, and platform threads have different identifiers. Asking the reviewer to choose among them makes the output contract harder to follow.

The old behavior only hid the gap

Earlier local reports could say “ready” because they ignored old findings. That did not close the finding; it merely stopped considering it when readiness was calculated.

What do we want instead?

1. Show one keyEvery earlier finding or finding discussion gives the reviewer the same durable finding key.
2. Copy the keyThe reviewer copies that key when an issue continues, changes, is fixed, or should be dismissed.
3. Apply the outcomeReviewPhin calculates one lifecycle outcome, updates a platform thread when needed, and commits the same saved state.
  • The reviewer uses one opaque finding key and never constructs or edits it.
  • ReviewPhin assigns a key to a new finding. On later reviews, the reviewer can only copy a key that ReviewPhin supplied in the earlier-finding or discussion context.
  • The existing findings and prior-outcomes collections remain; no second collection is added for local findings.
  • A current finding links to the key of the earlier finding it continues or replaces. A prior outcome uses that same key to resolve, dismiss, or reply about the earlier finding.
  • A closure must be explicit. Omitting an earlier finding never silently marks it fixed.
  • Platform thread and comment identifiers stay inside publication and conversation handling where they are actually needed.
  • Published and no-publish findings produce the same saved status and the same readiness answer.
  • Existing stored findings and mappings are reused without a new database column or migration.

How do we fix it?

Problem Planned change
Earlier findings and discussions expose different identifiers. Give both prompt inputs the same durable finding key. Remove platform addresses from the reviewer-facing finding contract when the reviewer does not need them.
A current finding must point back to an earlier issue. Keep the existing finding object and let it copy the earlier finding key. ReviewPhin uses that link even when the title, wording, or line has changed.
A closure currently names only a discussion. Keep the existing prior-outcomes collection, but make every entry name the durable finding key. Do not add a second local-only outcome collection.
A finding may or may not have a platform thread. Always update saved finding state through the durable key. If a mapping exists, also update or resolve that platform thread.
An unknown or ambiguous key could target the wrong issue. Validate every copied key against the context supplied to the reviewer. An unknown key never changes earlier saved state or a platform thread. A current finding with an unknown earlier key is still saved as a new finding so the issue is not lost. If one key maps to several live threads, the saved finding may still be updated by its exact key, but all platform mutations for that key are skipped. Record both cases as structured diagnostics.
Older saved results contain the previous identifiers. At the stored-result read boundary, retain their overview and findings but discard historical lifecycle pointers that name only a discussion or thread. Those pointers are not displayed in reports and cannot be converted safely into finding keys. The current model contract accepts only finding keys.
Important boundary: this plan unifies identifiers for the reviewer’s finding lifecycle. A conversational reply still needs the exact message or thread target supplied to the chatter role. Do not force finding keys into unrelated reply routing.
Lifecycle rule: a linked current finding means the concern continues. If its newly calculated key differs from the copied earlier key, ReviewPhin retires the earlier finding and saves the current one as its replacement. A key cannot be both continued and resolved or dismissed in the same response. Duplicate or contradictory references make the response invalid before any lifecycle change is applied.

Work steps

  1. Build one finding-key lookup. Combine earlier saved findings and bot-owned finding discussions by their durable key. Keep every matching live thread so duplicate mappings are detected instead of overwritten. Keep conversation-only routing out of this lookup.
  2. Give prompt inputs one finding key. Add the durable key to earlier discussion context and stop exposing unnecessary platform addresses to the reviewer. Keep the same key already present on saved prior findings.
  3. Simplify the current response contract. Reuse the existing finding and prior-outcome objects. Make both copy the durable key. Keep only resolve and reply as prior-outcome actions; a linked current finding already represents keep or update. Require either resolved or dismissed for closure, and require the reply body for a reply. Generate the prompt schema from the strict current response schema, with no legacy alternatives.
  4. Make the prompt rules direct. Tell the reviewer to copy keys exactly, link every continued issue, explicitly close fixed or invalid issues, and leave an issue open when the evidence is uncertain. Remove instructions that still ask for a discussion identifier.
  5. Project one lifecycle outcome. Turn only validated closures and replacements into an in-memory transition set. Project active findings from that set, then calculate readiness. Published and no-publish runs must compute the same outcome, and neither may infer a closure from omission.
  6. Update the platform when possible. Resolve or update a mapped GitHub or GitLab thread from the same finding key. With no matching thread, a closure remains local, a linked current finding gets a new thread when publishing is enabled, and a requested reply is skipped with a diagnostic. One match is safe to mutate. More than one match is ambiguous, so skip the platform change while preserving the saved finding outcome.
  7. Commit the saved lifecycle safely. After the platform phase succeeds—or immediately when publishing is disabled—apply the same transition set while the run still owns the job, then save the final result. A failed platform phase must not commit closures or replacements that a retry can no longer see.
  8. Keep old reports readable. Normalize historical results only when they are read. Drop old discussion-only lifecycle pointers, retain report content, and do not weaken validation of a new model response to accommodate old data.
  9. Test complete lifecycles. Cover two local runs, two published runs, changed finding text and anchors, unknown keys, duplicate thread mappings, contradictory output, old saved output, claim loss, and matching readiness across reports and platform summaries.

How do we know it works?

  • A first no-publish run stores one open finding. A second no-publish run explicitly resolves it, stores the old finding as resolved, and produces a ready report.
  • Resolving the same kind of finding after publication updates the stored status and resolves the matching platform thread when the platform supports it.
  • A current finding can link to and replace an earlier finding even after its title, explanation, file line, or anchor changes.
  • Merely omitting an earlier finding leaves it open and keeps readiness conservative.
  • An unknown key does not change an earlier finding or any platform thread. A duplicated thread mapping does not block an exact saved finding outcome, but it changes no platform thread. Both cases leave a structured diagnostic with the key and skipped action.
  • Duplicate references and a response that both continues and closes the same key fail validation before saved or platform state changes.
  • If publication fails before reconciliation finishes, the run does not commit its prior-finding closures or replacements. A retry can still see the earlier open state and complete the platform work.
  • The current prompt schema contains one finding identifier and no legacy discussion-address alternative for finding lifecycle actions. Prior outcomes expose only strict resolve and reply variants.
  • Older saved results still open in CLI reports and incremental history loading without weakening current model validation.
  • Platform summaries, stored reports, and later review context all agree about the same set of active findings and readiness.
  • Chatter can still reply to an exact requested comment or thread; finding-key cleanup does not break conversation routing.
