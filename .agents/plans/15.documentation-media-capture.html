Plan 15 · Documentation media

Show the workflows readers need to recognize.

Replace four published media placeholders with useful evidence of setup and review behavior. Correct the surrounding instructions first, then capture small reusable scenes with an automated local workflow and supervised platform recordings.

ImportanceMedium
Who noticesDevelopers and operators
Main areaDocs and capture tooling
Stored dataNo production changes
Finished result: Readers can recognize a working installation, configure the platform handoff, trigger a review, and find its output. Every visual has a purpose, a text equivalent, and a reproducible source scenario.

What is wrong today?

Four placeholders, no walkthrough assets

The docs home, Docker, merge request, and pull request pages display production notes asking for recordings. The docs asset directory contains a favicon; the platform illustrations have not been captured.

The difficult handoffs are missing

GitHub App registration crosses a terminal, ReviewPhin setup pages, and GitHub. GitLab requires manual webhook configuration. Neither journey has screenshots, although both require recognizing unfamiliar controls.

Some proposed scenes promise too much

A 90-second setup montage omits credential preparation and GitLab webhook creation. A 20-second first Docker boot hides image build time. A pending GitHub review is an intermediate publication state, not the result a reader should look for.

More motion is not always useful

The homepage already has a decorative review illustration and styled command examples. Reference tables, command disclosures, and text diagrams are useful existing media. Replacing these with recordings would make them harder to scan and copy.

Audit boundary: Checked the documentation media inventory, homepage composition, and source behind the proposed setup and review scenes. This is a plan, not a completed live GitLab or GitHub rehearsal. Platform UI labels, account permissions, and actual model output still require capture-day verification. Unrelated storage and provider reference content has not received a full factual audit.

What do we want instead?

1. Verify the claimTrace behavior to code and rehearse prerequisites.
2. Capture the evidenceRecord one observable action and its real result.
3. Publish and maintainPlace it beside the task, with captions and a refresh rule.
  • Use screenshots for locating controls and understanding output; use video only where an action or transition matters.
  • Keep all commands copyable and every essential step in text. Put media after the explanation it supports.
  • Use GitLab first and give GitHub its own complete setup and review coverage.
  • Never present an edited wait as a speed promise, or a sample page as a real connected account.

Work steps

  1. Prepare the production Docker path. Add a standalone Compose configuration with a full release image tag, the worker environment, health check, port mapping, and persistent mounts. It must run without application source or an image build. Extend the existing Happy Changelog post-version script to update and commit the image tag with the other release version changes. Point Docker setup instructions and the capture scenario at this file; retain source-build instructions as a separate development path. Use a published release for the demo, since a version bump can precede image publication. Keep public URL, model authentication, persistence, and HTTPS setup explicit.
  2. Fix and rehearse the text. Apply the corrections above and reconcile the two authentication documentation plans. Verify a complete setup on each demo platform before recording. If a step fails, keep the explanatory text and mark the scene blocked in the manifest rather than generating a convincing success screen.
  3. Build a small capture kit. Use TypeScript to coordinate fixtures, health checks, scene assertions and export metadata. Reuse the repository's Node and pnpm toolchain. Keep recording dependencies in development tooling. Do not introduce a media backend or a second docs framework.
  4. Automate local scenes first. Capture the local setup sample gallery with Playwright and terminal scenarios with VHS. Run repeatable renders in pinned Linux containers or WSL2 on Windows. Model-backed scenes still require credentials and are opt-in. A deterministic sample render verifies presentation, not a working integration.
  5. Capture live platform scenes under supervision. Seed disposable repositories through platform APIs, then use Playwright for browser framing and recording after authentication. Keep App creation, login, permission choices, and cleanup supervised. Assert semantic page states with bounded waits, not fixed delays. Record real model results without promising identical prose across reruns.
  6. Export and place the first batch. Ship B–E stills and A, D, E clips first, then optional setup clips. Add F and G next; assemble H last. A still can ship before its companion video. Remove the corresponding published placeholder when the still and complete instructions are ready.
  7. Make refreshes routine. Store a scene owner, source revision, platform version/date, prerequisites, commands, expected state, duration, alt text, transcript, artifact hashes, and source-file dependencies in one manifest. Flag affected scenes when their dependencies change; manually review remote UI at release time and at least quarterly.

How do we know it works?

  • The production Compose configuration runs a tagged published image without a source build. Happy Changelog updates and stages that tag with every release version bump, and a repeat of the same bump leaves it unchanged. Docker docs and recordings use this path.
  • All four media placeholders have been replaced or removed, and the text alone completes the task. The overview can remain a linked diagram until its video is ready.
  • A new reader can identify the GitLab webhook fields, the GitHub installation completion, the Run Review action, an inline finding, and the summary without scrubbing a video.
  • The Docker scene distinguishes server health from review readiness. Live platform scenes end on actual published output; sample scenes are labeled.
  • Each asset has an owner, verified revision, reproducible scenario, accessible text equivalent, and reviewed export. Credential-free local scenes can be regenerated with one documented command.
  • Videos have controls, posters, captions and transcripts. No autoplay is needed. Mobile layout, keyboard focus, reduced motion, and no-JavaScript reading work.
  • Public and container builds both load media, including under a path prefix. No runtime setup, health, or webhook routes are shadowed.
  • Capture failures stop that export with useful diagnostics; approved existing assets remain intact. No unattended job publishes live reviews or uploads raw recordings.

Checks to run: targeted formatting, plan links, docs/media validation, docs builds, desktop and narrow browser inspection, and a human review of each final capture against its adjacent text.
